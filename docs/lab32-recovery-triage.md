# GoGoGo Lab 32 — 异常退出与恢复取证

## 目标

减少安卓手机上排查「Shizuku 撤权／应用被强停／系统杀进程／GMS 关闭回调」时反复翻页面的工作。新增 **异常退出与恢复取证**，位于「实验与诊断」及「一键基础快检」中。

本轮不执行自动修复，不触碰 ServiceGo 模拟位置发布逻辑，不主动注册/清理任何 test provider，也不请求 Shizuku 权限。

## 读取的现有证据

1. 使用 LabServiceLifecycleJournal 已有的 boot-count / 单调时钟 / 进程代次判断，新增类型化只读接口 currentVerdict，不解析中文 UI 文本。
2. 从 Lab 25 私有 SharedPreferences 读取 GPS、NETWORK、FUSED 的启动扫尾和服务清理六组历史结论：REMOVE_RETURNED、ALREADY_ABSENT、PENDING、SECURITY_DENIED、OTHER_FAILURE 或无记录。
3. 如果先前的一轮是 PENDING、现在已有完成结果，额外提示「更早一次曾 PENDING」。这只是历史证据，不能误报现在仍有残留。
4. 按当前 ServiceGo 代码中的真实异步事件前缀区分 GMS DISABLE_SUCCEEDED、DISABLE_REQUESTED、关闭失败/权限拒绝、其他事件与无记录。**只记录最近一次事件**，不会断言当前 GMS mock 已关闭。
5. 自愿点击「保存当前摘要作为基准」时，只把精简报告保存到此应用的私有偏好，不保存坐标、网络/设备标识或原始系统日志。再次打开后可对比；「复制隐私精简报告」需用户手动触发，内容进入系统剪贴板。

## 两个关键限制

- API 返回 REMOVE_RETURNED 不等于系统一定没有残留 test provider；上一次回调 DISABLE_SUCCEEDED 不等于别的应用的缓存也已清空。
- 非正常结束可能发生在没有 onDestroy() 的情形。历史进程/会话状态只能提示风险，不能证明微信当前使用了何种定位源，也不能从这里判断第三方防护机制。
- 当前服务标记仍 RUNNING 时，页面明确提示不要执行破坏性的 Provider 清理。
- 旧事件可能属于上一轮会话，文本必须始终保留「历史」说明。

## 自动化测试

11 个纯 Java JUnit 用例覆盖：无历史数据、当前 PENDING、权限拒绝、过往 PENDING 但本次成功、GMS 请求尚未确认、GMS 关闭失败/晚到 enable、活动服务不建议破坏性清理、重启不确定性、隐私无识别内容、基准对比、不识别的未来结果不能误判成功。
