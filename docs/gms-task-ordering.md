# GMS 开启、发布与关闭顺序

2026-10-23，候选版本 `2.4.30-gms-ordering` / `2400098`，继续同一个 PR #59。包含此前的 Framework Provider 生命周期、海外坐标和回放输入修复，可直接覆盖安装。

## 已确认的客户端竞态

既有请求编号能够阻止旧回调覆盖新审计记录，也能阻止旧服务再次补发关闭请求，但已经发出的 `setMockMode(false)` 仍可能与下一服务的 `setMockMode(true)` 重叠。此前每服务自己的坐标单请求门闩也没有等待上一服务未完成的 `setMockLocation`。这属于本应用请求顺序的问题，没有证据证明它就是微信或无线抖音失败的根因。

## 实现

- 所有 ServiceGo 共用 GMS 异步完成队列。开启模式、发布坐标、关闭模式均要等前一个 Task 的终态回调后才开始，普通方法返回 Task 不会释放队列。
- 停止时丢弃待发坐标，关闭排在旧 Task 之后；下一服务的开启排在此关闭之后。已停止服务的迟到开启回调不再另外补发关闭。
- 每服务至多一个正在发布的坐标和一个最新待发坐标，慢任务期间合并旧坐标。GMS 调用与其回调使用独立工作线程，不占用主线程，也不阻塞 Framework Provider 发布队列。
- 成功、失败和取消均记录为各自终态。同步调用异常与“Task 已返回但回调无法观察”分开：后者保持该 GMS 队列等待，不以超时假定完成；若后来收到真实回调，可以继续并重新归类未知计数，避免同一 Task 重复计数。
- 既有请求所有权审计继续保留，新增排队／取消／未观察到完成的事件进入原诊断报告，不新增页面。

## 验证及边界

回归覆盖旧开启尚未完成时停止并重启、旧坐标 Task 尚未完成时关闭、坐标合并、重复完成回调、启动前已停止、未知完成、调度异常及跨线程回调；另验证迟到完成计数和排队状态不会被当成关闭成功。完整构建、Lint 和打包检查由开发侧运行，手机正常使用不增加步骤。

这提供本进程基于公开 Task 契约的调用顺序，不是 Google Play services 内部或跨进程的物理事务锁。若 Task 永不完成或其回调始终不可观察，后续 GMS 操作会等待，不能保证停止时已恢复真实定位；进程被终止也不能保证异步清理完成。GPS／NETWORK／Framework FUSED 继续独立运行。

覆盖安装更新包内 `Go_` 主程序即可，无需逐版安装或导入 Demo。无需 Root、电脑或以太网；没有更改网络接入、Wi-Fi／蜂窝扫描、VPN 出口或第三方应用内部服务。微信实时共享、无线抖音及海外地点功能仍没有新的手机成功证据，不把本轮云端验证当作这些目标的验收。
