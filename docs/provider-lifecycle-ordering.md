# 停止、重启与发布顺序

2026-10-23，候选版本 `2.4.29-provider-lifecycle` / `2400097`。在同一个 PR #59 内继续开发，包含此前的[海外移动坐标与回放校验](location-coordinate-correctness.md)，不要求先安装中间版本。

## 解决的问题

此前退出最多等待发布线程 350 毫秒，然后在主线程清理 Framework Provider。如果旧发布仍在系统调用里，失败后的移除／重注册可能晚于退出清理，重新留下模拟 Provider；紧接着启动新服务也可能与旧清理交叉。

现在同一进程的所有 ServiceGo 实例共享一个异步 FIFO 工作线程。Framework Provider 的冷启动扫描、注册、发布、权限观察回调中的清理，以及最终清理都在此线程执行。停止时拒绝新任务、丢弃待发布坐标，将最终清理排在已有操作之后；新服务注册排在旧清理之后。主线程不等待这些 Framework Provider 系统调用返回。

发布最多保留一个正在执行的坐标和一个最新待发布坐标；系统调用慢时合并旧坐标，避免持续积压。GPS、NETWORK、Framework FUSED 和 GMS 发布入口继续使用同一份不可变坐标快照。GMS 异步请求仍受原有的请求所有权与单请求门闩约束。

服务生命周期和 Framework 清理分别记日志。清理尚在队列、已尝试和阶段异常分别记录；旧服务的完成回调不能覆盖新服务的记录。仅执行过清理不代表系统已恢复真实定位，权限失败仍以逐 Provider 的既有审计为准。诊断读取缓存快照，不等待 Provider 系统调用。

## 开发侧验证

新增并发回归覆盖阻塞中的旧发布晚返回、停止后待发布／权限回调丢弃、新服务注册顺序、慢调用只保留最新坐标、异常后继续执行以及队列拒绝。构建、Lint 和打包校验由开发侧完成，不增加手机实验页。

## 手机使用及范围

覆盖安装更新包中的 `Go_` 主程序，按原方式选点和使用；无需安装或导入 Demo。无需 Root、电脑或以太网。日志仍在诊断中心一次复制，用户可稍后统一反馈。

这修复的是本应用的发布与清理顺序。系统调用如果始终不返回，后续清理和新注册仍会等待；进程被系统终止时，也不能保证异步清理完成，下次启动继续执行冷扫描。没有手机实测证据证明微信实时共享、无线抖音或其海外位置功能已成功，不能把云端回归当作这些目标的验收。
