# GoGoGo Lab 34 — 历史取证时间窗校验

## 为什么需要这轮

Lab 32/33 的诊断会读取上一次 Provider 清理和 GMS 关闭的历史枚举，但没有把事件时间与最近一次 ServiceGo 启动时间作比较。只要 App 曾发生过一次 PENDING / SECURITY_DENIED 或 GMS DISABLE_REQUESTED，即使后来重新启动并进入新一轮模拟，旧失败也可能被排成“本次优先查恢复”，误导手机排障。

本轮**只修改诊断层**；模拟、路线、地图、Shizuku 授权和 Android test provider 生命周期均保持不变。

## 采用的保守做法

- 从现有 Lab 23 服务日志读取最近一次启动 wall-clock 时间（只读）。
- 从现有 Lab 25 审计记录读取 GPS/NETWORK/FUSED 的启动扫尾和服务清理 started_at 时间，以及 GMS gms_last_at。
- 三类时间标记：
  - **时间在最近一次服务启动之后**：只能表示墙上时钟顺序接近最近一次启动；不证明是同进程、真实事件关联或外部消费者已刷新。
  - **早于最近一次服务启动（旧记录）**：属于较早的时间区间；依然展示但**不当作最近一轮的失败警报**。
  - **时间关联无法确认**：缺少时间戳、缺少启动记录，或者系统时钟可能被手动回拨。保留未知，不能自动宣称成功。
- Lab 32 页面逐项展示时间标签。以前的 PENDING 仍保留历史提醒，但是明确不证明现在有残留。
- Lab 33 综合排障的优先级不会因为**已确认早于最近一次启动**的旧 Provider/GMS 失败，就将当前诊断强制切换到“恢复故障”。
- 对 PENDING/SECURITY_DENIED/OTHER_FAILURE 或 GMS disable 未完成且时间不明的事件仍采取保守策略，引导用户进一步核实。
- 不保存或导出精确事件时间戳、设备 ID、坐标、IP、SSID、日志；现有诊断报告中的标签只表示相对关系。

## 自动化测试

新增 LabEvidenceTimeWindowTest 共 11 个 JUnit 用例：
- 旧于启动时间、恰好等于启动时间、晚于启动时间；
- 未记录服务开始时间、未记录事件时间、时钟回拨导致未来事件；
- 历史 PENDING 不应阻塞本轮分析；
- 旧 GMS 失败/请求不应误报本轮关闭失败；
- 最近时间窗内的权限拒绝与请求未确认仍然提示人工核查；
- 无法确认的时间不能伪装旧记录；
- 旧 GMS 成功事件也不能证明现在的真实消费结果。

## Android 13 真机验收

- [ ] 原有 Preview 包名与公开测试签名相同，可直接覆盖，数据和 Lab 31/32/33 的基准均保留；签名冲突时不要卸载。
- [ ] 完成一轮标准模拟启停后，实验与诊断 → 异常退出与恢复取证，Provider 与 GMS 显示相对时间标签。
- [ ] 修改模拟位置应用、撤销 Shizuku、模拟被强停等情况，只观察日志，不在诊断页自动恢复或改动系统 AppOps。
- [ ] 下一次重新启动服务后，前一轮失败记录应带“旧记录”；综合排障不应把它冒充当前清理失败。
- [ ] 本次真正 PENDING 或权限失败依然能明确引导核对实验仪表盘，不做成功宣称。
- [ ] 系统时钟手动变化或缺失时间戳时显示“时间关联无法确认”，绝不当作本轮清理成功。
- [ ] 剪贴板摘要仅显示时间关系（非完整时间戳/坐标/设备标识），现有消费者矩阵和模拟功能均可使用。
- [ ] 独立执行 Android 13、不同厂商设备上的 Provider 清理、GMS 缓存和微信实际位置黑盒测试；绿色 CI 无法代替验收。

## 当前限制

时间窗依据的是**墙上时钟**而非不可伪造的跨进程会话标识。系统时钟变动、异步回调晚到等情况不能完全分辨；因此所有标签均是供人工排查参考的历史关系，**不是现存 test provider 或微信定位状态的证明**。
