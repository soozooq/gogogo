# 定位启动正确性修复

2026-10-21，候选版本 `2.4.27-location-startup` / `2400095`。

用户要求继续实际定位开发，减少逐项实验，稍后一次回传。这一轮不扩展 Demo、实验面板或要求先交旧测试记录。

## 修复的问题

原服务在 `onCreate()` 中立即启动 33ms 发布线程，此时坐标仍是内置默认值；用户选中的目标、路线或系统重启恢复目标，要等 `onStartCommand()` 才写入。初始化较慢时，可能先向系统发布默认济南坐标。

空 Intent、未知命令，以及无效路线缺少早返回，也可能落入手动启动分支，使用缺失字段的默认济南坐标并保存。它们不能代表用户选择了该位置。

本轮让发布等待有效目标完成初始化，拒绝不完整或无效目标；目标更新与发布帧构造保持一致，同一帧的各条通路使用同一组经纬度与运动信息；已经提交给系统的在途调用不能撤回。保留 GPS、NETWORK、可用时的 framework FUSED 和 GMS FLP 原通路。不改变网络类型、Root 权限、第三方应用进程或业务接口。

## 日常使用

1. 下载本轮手机更新包，解压并覆盖安装 `Go_` 开头的主程序，不卸载旧版。
2. 按原方式选择目标并开始模拟。无需导入 Demo 或逐项重跑旧实验；包内 Demo 仅保留给高级工具，可忽略。
3. 下次回传时，在诊断中心点一次“复制最近诊断日志”。该出口已汇总定位诊断和已保存的应用运行记录；不触发新实验，不自动上传。

## 证据范围

这修复的是自有定位发布链路的确定错误，**不是已找到微信、无线抖音或海外定位的通用修复**。现有引擎没有以太网前置条件；第三方应用是否采用模拟坐标、海外地点是否加载和是否发送成功，仍不能由本工程单测或构建证明。

构建、单测、实际 APK 校验和目标手机效果分别记录。用户可以稍后一次统一回传，不再把逐个 Demo PASS 作为继续开发的条件。此前容器工单的“不可修改 ServiceGo”适用于当时 V3.1 首次运行任务；当前用户明确要求继续核心定位开发，本轮为后续独立修复，原容器逻辑保留。
